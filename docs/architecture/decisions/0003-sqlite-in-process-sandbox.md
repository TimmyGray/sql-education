# ADR-0003: In-process SQLite for untrusted SQL execution

> **Summary:** Student SQL runs in an embedded SQLite database (a fresh in-memory DB per request, inside a worker thread) instead of a separate PostgreSQL instance.
> **Status:** Accepted
> **Date:** 2026-06-07

[← Back to docs index](../../INDEX.md) · [Architecture overview](../overview.md)

---

## Context

[ADR-0002](0002-isolated-sql-sandbox.md) ran untrusted student SQL on a second PostgreSQL server (`sandbox-postgres`, port 5433) with a restricted `sandbox_runner` role. That works, but for a deployed portfolio project it means **provisioning and paying for a second hosted database** purely to evaluate small, read-only queries against tiny fixtures.

Two things make a lighter approach viable:

1. The sandbox already sits behind a clean abstraction — the abstract `SandboxRunner` (`apps/api/src/sandbox/sandbox-runner.ts`). `GradingService` depends only on that token, so the execution engine is swappable without touching the grading pipeline.
2. The grader compares the student result against a **baked** `expectedResultJson`. As long as those expected values are generated by the *same* engine that runs student queries, engine-specific formatting (numeric precision, auto column names, date strings) stays self-consistent.

The cost ADR-0002 cited against SQLite — "students learn non-transferable syntax" — is acceptable for this product: the curriculum is introductory, and the differences at NOVICE/JUNIOR level are minimal.

## Decision

We will execute untrusted SQL **in-process using embedded SQLite** (`better-sqlite3`):

1. Each grading request opens a brand-new `:memory:` database containing **only** the task fixture (`setupSql`), runs the student query, returns the rows, and discards the database.
2. Execution runs inside a **worker thread**. Because `better-sqlite3` is synchronous, a pathological query (e.g. an unbounded `WITH RECURSIVE`) would block the event loop; the parent enforces the 2-second cap by calling `worker.terminate()`, turning a potential stall into a clean `TIMEOUT`.
3. The curriculum now targets **SQLite dialect**. `prisma/seed/validate.ts` bakes every `expectedResultJson` against SQLite, so a correct student query matches the expected output exactly.

Isolation is structural rather than role-based: the in-memory DB holds nothing but the fixture, so untrusted SQL has no other data to read or corrupt and nothing to tear down.

## Consequences

**Positive**
- No sandbox database to provision, host, or pay for — the sandbox is just code.
- Isolation is simpler and stronger by construction: a fresh empty DB per request, no shared role, no cross-user state, no teardown.
- Faster cold start and per-request setup (no network round-trip, no connection pool).
- Local dev and CI need one fewer service.

**Negative / trade-offs**
- The platform teaches **SQLite** dialect, not PostgreSQL — this reverses the core concern of ADR-0002.
- `better-sqlite3` is a **native dependency** (needs a prebuilt binary or a build toolchain in the Docker image).
- A synchronous engine needs a **worker thread** for a hard timeout; runaway queries also bounded by a `MAX_RESULT_ROWS` cap.
- Every `expectedResultJson` had to be re-baked, and a few Postgres-only tasks rewritten (see follow-ups).

**Follow-ups**
- `validate.ts` re-bakes against SQLite; rerun it after any change to `setupSql` or a reference query.
- Rewrote dialect-specific tasks: `junior/block4` (`EXTRACT`/`INTERVAL`/`SUBSTRING…FROM…FOR` → `strftime`/`julianday`/`SUBSTR`), `middle/block3` task 8 (`> ALL` → `> (SELECT MAX …)`), `middle/block5` tasks 7–8 (`ROLLUP` → `UNION ALL` subtotals).
- A pooled worker is a possible later optimization if grading throughput becomes a bottleneck.

## Alternatives considered

| Option | Why not chosen |
|--------|----------------|
| Keep the second PostgreSQL sandbox (ADR-0002) | Extra hosted database to run and pay for; the main reason for this ADR |
| `sql.js` (SQLite compiled to WASM) | Pure-JS (no native build) but slower with a clunkier API; still needs a worker for timeouts |
| `node:sqlite` (built-in) | Zero dependency, but still experimental and needs the `--experimental-sqlite` flag on Node 22.x |
| In-process SQLite without a worker | A synchronous runaway query would block the event loop — no reliable timeout |
